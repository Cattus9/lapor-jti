## 1. [P1] Migration dapat gagal pada penyerahan lama yang sah

Lokasi: `drizzle/0020_satpam_handover_contact_and_photo.sql:15`; aturan yang sama berada di `src/db/lost-found-schema.ts`.

Migration menambah kolom kontak yang bernilai NULL pada data lama, lalu langsung memasang CHECK yang hanya mengecualikan `legacy` atau penyerahan sebelum **6 November 2026 pukul 17.00 WIB**. Aplikasi sebelum commit ini memperbolehkan penyerahan nonlegacy tanpa kontak, termasuk setelah waktu tersebut.

Jika database laptop anggota memiliki penyerahan semacam itu, pemasangan CHECK akan gagal karena baris lama ikut diperiksa. Batas tanggal tetap tidak mewakili waktu deployment setiap laptop. Dokumentasi OPERATIONS.md yang menyebut migration ini tetap kompatibel dengan data lama belum benar untuk kasus tersebut.

Di Compose, app menunggu service migrate selesai sukses (`compose.yaml:61`). Karena itu masalah ini dapat menghalangi startup app versi baru. Belum dibuktikan bahwa database pengguna saat ini memiliki baris pemicu; temuan ini berdasarkan kondisi SQL dan kontrak aplikasi lama.

Perbaikan: rancang pengecualian/backfill eksplisit untuk seluruh penyerahan sebelum upgrade, tanpa mengarang kontak atau menghapus data. Uji database baru dan upgrade database lama yang berisi penyerahan setelah batas tanggal. Jika migration sudah digunakan pihak lain, tentukan strategi perbaikan berdasarkan journal dan keadaan database; jangan sembarang mengedit atau menghapus migration terapan.

## 2. [P2] Retry foto meninggalkan file dan tidak memeriksa perubahan isi foto

Lokasi:

- `src/features/lost-found/application/satpam-service.ts:29` dan `:88`.
- `src/features/lost-found/infrastructure/drizzle-inventory-repository.ts:138`.
- `src/features/lost-found/infrastructure/drizzle-satpam-repository.ts:243`.
- `src/features/lost-found/components/inventory-detail-dialog.tsx:152`.

Kedua jalur penyerahan menyimpan file baru sebelum repository memeriksa submissionKey. Repository mengembalikan sukses untuk retry identik, tetapi service hanya membersihkan file ketika ada exception. File dari retry sukses tidak ditautkan dan tidak dibersihkan.

Reproduksi service tanpa database, memakai repository idempotent dan storage pencatat operasi: dua panggilan handoverInventory identik menghasilkan `stagedPhotos: 2`, `removedPhotos: 0`. Satu file tambahan tidak terpakai. Ini reproduksi dengan mock, bukan tes integrasi PostgreSQL.

Selain itu, fingerprint server hanya mencakup actor dan data teks, tidak mencakup isi foto. Pengiriman ulang dengan key sama tetapi foto berbeda dapat tetap dianggap identik dan mengembalikan sukses dengan foto lama. UI inventaris hanya memasukkan keberadaan foto ke fingerprint; mengganti satu foto dengan foto lain tidak menjamin key baru.

Perbaikan: sertakan digest konten foto dalam kontrak idempotensi server, lalu bersihkan file sementara yang tidak dipakai pada hasil reuse sukses, di kedua jalur penyerahan. Jadikan hasil repository cukup jelas untuk membedakan reuse dari penyimpanan baru. Pola cleanup reuse sudah tersedia pada createInventory dalam service yang sama.

Tes yang diperlukan: retry setelah respons hilang, foto berbeda dengan key sama, kegagalan transaksi, dan retry bersamaan. Perlindungan baris penyerahan ganda tetap ada; masalah ini mengenai file dan konsistensi bukti foto.

## 4. [P2] Ganti laporan terkait dapat mempertahankan identitas penerima sebelumnya

Lokasi: `src/features/lost-found/components/inventory-detail-dialog.tsx:249`.

Pada penyerahan inventaris tanpa linkedLoss tetap, memilih laporan A mengisi otomatis nama/kontaknya. Ketika pilihan diganti ke laporan B, selectedLoss berganti tetapi nama/kontak hanya diisi bila masih kosong. Isian A tetap dipakai meskipun laporan terkait menjadi B.

Jika pengguna mengandalkan autofill lalu menyimpan, catatan dapat berisi penerima A sekaligus menyelesaikan laporan B. Nama penerima memang tidak selalu harus sama dengan pelapor; masalahnya adalah data autofill usang tanpa penegasan setelah pilihan berubah.

Perbaikan: bedakan isian otomatis dari edit manual. Perbarui/bersihkan isian otomatis ketika laporan berubah dan pertahankan edit manual dengan konfirmasi yang jelas bila diperlukan. Uji pilihan A → B → tanpa laporan web.
